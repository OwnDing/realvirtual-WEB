## 2. AGPL 定性

依据仓库 [LICENSE](../../LICENSE) 第 0、1、4–7、10、13 条：软件副本、修改、安装、维护与保证服务可以收费；对受覆盖的修改版，应落实对应源码和下游权利义务。不能通过单独合同把依法复制、修改、再分发改成必须再次付费获准。客户已有版本的许可权与后续服务期限分开。

“没有上游商业授权书”本身不阻断遵守 AGPL 的商业使用。AGPL 是权利来源之一；不需要因本次选定路线自动采购闭源许可。上游公开条款 §13.1 也区分 AGPL 与商业许可。公开条款适用于本项目历史版本的范围仍须结合获取时证据判断。[上游现行条款](https://realvirtual.io/en/terms/)

对应源码应匹配实际交付版本，包含修改、构建/安装所需脚本和适用的接口定义等；压缩 JS、当前默认分支、只给原上游仓库链接都不能自动代替。为避免离线客户无法取源，建议把可修改源码包直接随交付包提供，并在界面提供明确的同源获取入口。若选书面要约等其他履约方式，由律师按具体分发方式审定；不能机械套用统一保存年限。

交付浏览器程序/安装包要分析副本传递；修改版的远程交互还须分析 §13。对受适用条款覆盖的网络用户，源码入口不能额外设置“仅付款人可取源”的限制。无需无条件向全世界公开一切，但接收者获得的依法再分发权必须保留。英文原文由 [OSI 的 AGPL 正文](https://opensource.org/license/agpl-3.0) 交叉核对，中文解释不替代原文。

纯业务数据、独立几何与可执行插件/脚本应逐项定性。不能认定“所有 GLB 都要公开”，也不能保证“所有模型都天然保密”。`rv_extras` 中执行逻辑、结合程序所需内容及导出时嵌入的程序属于重点审查对象。客户 NDA 应限定真正独立且有权保密的数据，不得限制 AGPL 已授予的代码权利。

## 3. 与上游的关系

目前可支持的关系表述是：**基于 realvirtual WEB 的独立修改/发行及实施服务提供方**，不是已获证明的官方代理、授权经销商、独家合作伙伴或原有代码所有者。商标使用、官方背书、商业支持、私有模块和 CONNECT 是独立事项，不能由 AGPL 代码许可推导。

保留原有版权与适用署名，并对可证明属于本方的修改注明修改事实/日期。源码里带上游版权头不意味着每份后来修改都已转让给上游；把项目改名也不意味着原有权利被买断。自己的新增成果归属须核对劳动/委托合同、贡献记录和可适用的许可协议。

### 署名的具体差异

- 本地历史提交 `b06e09a` 的 README 明确要求保留上游水印；同一提交 index.html 含 `rv-watermark` 和上游名称。

- 现行上游条款 §13.6 主张该署名属于 AGPL §7(b) 附加要求。其适用性/合理范围需审查；本计划不自行裁定无效，也不认为网页后来更新可自动追溯改变历史许可。

**建议按保留上游清晰署名设计 AGPL 交付，并让自有服务品牌与之并存。** “完全隐藏上游的白标”不再作为已获许可的承诺。产品修复需另按既有品牌规格和本次权利结论实施；本次只登记现状，没有修改界面。

## 4. 中国大陆销售边界

大陆销售不是绕过外国软件版权的依据。《计算机软件保护条例》涉及外国软件保护、修改/复制/发行/信息网络传播、职务和委托开发、许可与署名等事项。应以现行文本和实际合同为依据，不把营业执照、软件登记证书或代码量当成原有代码权利来源。[司法部法规库，2013 年修订文本](https://xzfg.moj.gov.cn/front/law/detail?LawID=581)

需要律师签收的具体输入是：签约主体、交付/运维主体、客户是否继续向其客户提供演示、程序与数据边界、雇佣/委托成果、贡献历史、历史交付记录和上游署名要求。若申请软件著作权登记，应准确说明原作来源和本方改进范围；不能把全部上游程序表述为独立原创。[国家版权局登记办法](https://www.ncac.gov.cn/xxfb/flfg/bmgz/202410/t20241015_869486.html)

## 5. 可采用的收入与合同结构

| 收费项目 | 建议约定 | 不应混入的限制 |
| --- | --- | --- |
| 版本交付/安装/验收 | 明确交付物、服务范围、里程碑和验收 | 不以交付费取消受覆盖程序的修改/再分发权 |
| 年度维护/升级 | 支持时段、响应等级、适用版本、更新渠道 | 停止续费不使已有 AGPL 权利失效 |
| 集成/定制开发 | 需求、工程费用、成果与源码边界 | 受覆盖修改不能靠 NDA 全面闭源 |
| 模型加工/内容服务 | 按有权处理/交付的独立资产约定 | 不声称来源不明模型均可转授权 |
| 培训/现场服务 | 人天、差旅、交付记录 | 不承诺未验证的工业安全或官方背书 |

自有离线许可证继续按 ADR-0007 作为合同/服务凭证，不得用“未经我方再次授权不得运行/改动 AGPL 程序”等条款绕过本路线。对创作保存降级、到期水印等既有行为应另做合同一致性审核；本次不把功能存在解释为法律认可。

## 6. 源码与声明交付方案（供实施验收）

每个正式版本至少准备：

1. 精确到提交、补丁和最终制品摘要的版本说明；记录未提交修改的来源，不只写版本号。
2. 对应源码及构建/安装材料：依赖锁、必要补丁、工具链说明、必要配置示例和自有修改；排除密钥、真实客户地址和未经授权资产。
3. 根许可证、适用附加署名、修改声明、实际交付组件的第三方正文/NOTICE；schema 的 CC-BY 声明独立保留。
4. LGPL/内嵌组件的精确源码、修改和适用替换/重链接履约材料；普通 npm 包的 MIT 标签不能替代内嵌库核查。
5. 离线客户可访问的源码获取入口与交付回执；网页访问权限和 AGPL 源码权利分别设计。
6. 干净环境按交付说明重建与核对；不能只证明开发机可以构建。

已有 demo-player 源码包生成器是可复用基础，不证明 WEB 工作台与整个 Appliance 都完成上述要求。Appliance 自身的 licenses/README 仍要求发行方补充精确对应源码/合法履约材料。
