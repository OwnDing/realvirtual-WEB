# 变更管理规范

## 1. 必须使用 ExecPlan

- 跨 `engine`、`hmi`、`project`、`plugins`、`interfaces` 等多个区域；
- 新的用户可见功能闭环或现有 UX 的系统性变化；
- GLB/rv-ODT、项目清单、持久化、配置、端口、信号或公共插件契约变化；
- 模型加载/清理、固定时间步、DES、渲染后端或性能关键路径变化；
- 工业接口、MCP 写工具、安全权限或外部系统集成；
- 数据迁移、跨版本兼容、预计跨会话或不能一次安全回滚的任务。

小型、局部、可一次验证和回滚的缺陷修复可以不创建 ExecPlan，但仍受宪法、AI 安全和 DoD 约束。

## 2. 必须使用 ADR

- 改变技术栈、模块边界、部署模式或状态所有权；
- 引入新的框架、持久化介质、服务端平台或跨插件协作模式；
- 改变 NodeId/路径/资产/文档/端口身份模型；
- 改变信号方向、写权限、仿真 Tick、事务或一致性语义；
- 对 Approved 架构或兼容性规则作例外；
- 在多个可行方案中选择一个会长期约束后续开发的方案。

## 3. 契约与迁移

- 已发布契约默认只加不减；破坏性变化必须采用“扩展 → 双读/双写或转换 → 切换 → 清理”的版本化流程。
- Schema、TypeScript 类型、加载器、写入器、fixture、文档和生成物必须同一任务同步。
- 未知字段必须保持；旧客户端不得在 read-modify-write 时删除新字段。
- 名称不得承担新稳定身份；多语言展示文本与 ID 必须分离。
- Agent 不得自行把 Draft 契约宣布为 Approved，也不得用“实现已经存在”绕过评审。

## 4. 并发开发

- 一项复杂任务对应一个活动 ExecPlan和明确的 Allowed/Forbidden Paths。
- 同一个正式 Schema、项目格式、配置优先级或公共插件接口默认单写者。
- 两个活动任务不得同时修改同一契约；必要时按依赖顺序串行合并。
- 修改前和交付前都要检查工作树，保留用户和其他任务的改动。

## 5. 文档变更

- Approved 文档的语义变化必须可审查，不与大规模格式化混在一起。
- 移动/重命名文档必须更新索引、仓库内链接、代码注释和旧文档登记表。
- 被替代的规范移入 `archive/`；阶段事实移入 `delivery/snapshots/`；外部研究移入 `references/`。
- 文档状态升级需要 Owner 审核；代码实现不能自动升级文档状态。

## 6. 交付顺序

复杂能力采用黄金切片：先冻结一个端到端、可观察、可回滚的最小闭环，覆盖正例、关键反例、保存恢复和浏览器行为；验证后再扩展到更多设备、语言、配置源或工业协议。不得用一个单元测试通过的子集宣称整个平台能力完成。
